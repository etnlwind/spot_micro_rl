# V28.2_PLAN.md

## 한 줄 정의
**V28.2는 V28.1에서 RL 살리기에 성공했지만 RR이 그 자리를 대신 무너진 패턴을 해결하는 버전이다.**
핵심 문제는 "rear pair 대칭 penalty가 3발 exploit reward를 이기지 못한 것"이며,
이를 penalty 강화 + 즉각 반응 구조 추가 + 모니터링 복원으로 해결한다.

---

## 분석팀 피드백 반영 (2026-03-16)

원안 방향은 타당하며 V28.2로 가는 판단도 맞음. 아래 3가지 보완사항 반영.

### 피드백 1. 과강도 리스크 — stage 3~4 완충 구간 추가

rear_symmetry_max -28, rear_contact_diff_max -15 등을 중반부터 너무 빨리 full strength로 올리면
학습 유연성을 죽일 수 있음.

**반영**: iter 700 이전은 약한 ramp (logging-only 또는 50% 수준), iter 800 이후 full enforcement.
Stage 3(400~700)은 "관찰 + 약한 개입", Stage 4(700+)부터 "강한 유지"로 분리.

| 구간 | rear_symmetry | rear_contact_diff |
|------|--------------|-------------------|
| iter 400~600 | 0 → -14 (50%) | 0 → -7.5 (50%) |
| iter 600~700 | -14 → -28 (100%) | -7.5 → -15 (100%) |
| iter 700+ | -28 유지 | -15 유지 |

### 피드백 2. rear_contact_diff_threshold — 0.10 단일 threshold 채택

threshold 0.15는 iter 1102 diff=0.116을 놓친다(문서 스스로 인정).
2단계 threshold가 이론적으로는 더 정밀하지만, V28.2 우선순위는 "안전하게 빨리 실험"이다.

**최종 결정 (기획팀)**: V28.2에서는 **단일 threshold 0.10** 채택.
- 0.10 미만: 무시
- 0.10+: full penalty

2단계 threshold는 구현 복잡도 + 디버깅 부담이 있으므로 **V28.3 후보**로 보류.
iter 1102 diff=0.116 → gap=0.016 → penalty 발동 (원안 0.15에서는 미발동이었음).

### 피드백 3. front_rear_balance 모니터링 유지

rear 비대칭만 강화하면 "rear 둘은 살렸는데 여전히 앞다리 중심 gait"가 남을 수 있음.
front_rear_balance는 reward term 조정 없이도 **heartbeat 핵심 모니터링 항목**으로 유지.

**반영**: heartbeat KPI에 아래 두 항목을 나란히 표시.
- `front_rear_propulsion_balance` (기존 유지)
- `rear_pair_residency_gap` (신규 추가)

## 2. 실패 원인 정확한 정의

### 원인 1. rear_pair_residency_symmetry_penalty 강도 절대적으로 부족

현재 max weight = **-8.0**.
iter 1502에서 rear contact EMA 차이가 0.4~0.5 수준이면 실제 penalty ≈ -8.0 × (0.5 - 0.05) ≈ **-3.6**.

반면 3발 exploit으로 얻는 추가 reward:
- RL이 강해질수록 `contact_residency` late reward (+4.0 × RL_ema), `forward_velocity` 상승
- RL usage 0.962 → contact residency reward 기여만 해도 수 units

**-3.6 penalty가 이 이득을 이길 수 없다.**

### 원인 2. EMA 리셋 후 비대칭 회복 — RR 이탈 사각지대

`_v281_residency_ema`는 episode 리셋 시 해당 env 초기화.
run 재기동 시 모든 env EMA = 0 → penalty = abs(0-0) = 0.

정책은 이미 RL을 선호하도록 형성되어 있으므로 EMA 워밍업 과정에서:
- RL EMA가 RR EMA보다 빠르게 올라감
- 이 격차가 커지기 전에 `rear_pair_residency_symmetry_penalty`가 충분히 반응하지 못함
- 격차가 일단 커지면 **3발 exploit이 stable local optimum이 되어 회복 불가**

이 "사각지대"가 iter 1002~1102 사이에 발생했다.

### 원인 3. current-step 즉각 반응 부재

`rear_pair_residency_symmetry_penalty`는 EMA 기반 → 최소 수백 step의 lag.
`rear_left_right_usage_diff_penalty` (현재 -10.0), `rear_left_right_propulsion_diff_penalty` (-20.0)는 current step 기반이지만:
- usage_diff > 0.40 threshold 이후에만 발동 (max_diff 파라미터)
- 이들도 reward 712를 이기지 못하고 있음

**즉각적이고 강한 current-step rear contact diff penalty가 부재하다.**

### 원인 4. heartbeat에 residency 지표 없음

`contact_band_residency_rl/rr`, `rear_pair_residency_gap` 등 V28.1 신규 지표가
**common.py에 보고 로직이 없어** heartbeat에서 전혀 보이지 않았다.
iter 1102에서 이미 rear_diff=0.217이었지만, 당시 heartbeat에서 "KPI 5개 양호"로 표시됨.
**모니터링 사각지대가 조기 개입을 불가능하게 만들었다.**

## 3. V28.2 핵심 수정 사항 (6개)

### 수정 1. rear_pair_residency_symmetry_penalty 3.5배 강화 (완충 구간 포함)

| 항목 | V28.1 | V28.2 |
|------|-------|-------|
| rear_symmetry_max | -8.0 | **-28.0** |
| rear_symmetry_ramp_start | 600 | **400** |
| rear_symmetry_ramp_end | 1000 | **700** |

**근거**:
- 3발 exploit 추가 이득 추정값 ~5~10 units에 대응하려면 penalty가 이를 초과해야 함
- gap 0.5 기준: -28.0 × (0.5 - 0.05) = **-12.6** — 충분한 억제력
- ramp를 iter 400~700으로 당기는 이유: iter 700에서 최대치 도달 → iter 800 이전 run 재기동 사각지대 해소

**완충 구간 (분석팀 피드백 반영)**:
- iter 400~600: 0 → -14 (50% 수준, 관찰 + 약한 개입)
- iter 600~700: -14 → -28 (100%, full enforcement 도달)
- iter 700+: -28 유지

### 수정 2. rear_contact_diff_penalty 신규 추가 (즉각 반응, threshold 0.10)

**새 reward term**: `rear_pair_contact_diff_penalty`

EMA 기반이 아닌 **현재 step contact_ratio 기반** penalty.
- 측정: `abs(contact_ratio_rl - contact_ratio_rr)`
- threshold: **0.10** (단일, 소폭 변동 무시)
- max weight: -15.0
- ramp: iter 300~600

수식: `penalty = clamp(abs(rl_contact - rr_contact) - 0.10, 0)`

**목적**:
- EMA 워밍업 사각지대를 current-step 즉각 반응으로 보완
- iter 1102 시점 diff=0.116 → gap=0.016 → penalty 즉시 발동 (원안 0.15에서는 미발동)
- iter 1201 시점 diff=0.284 → gap=0.184 → 강한 penalty 발동

> 2단계 threshold(0.10~0.18 약한 / 0.18+ 강한) 구조는 V28.3 후보로 보류.

### 수정 3. late_phase_band_exit_penalty 2.5배 강화 + 타이밍 앞당김

| 항목 | V28.1 | V28.2 |
|------|-------|-------|
| exit_penalty_max | -6.0 | **-15.0** |
| exit_penalty_ramp_start | 800 | **600** |
| exit_penalty_ramp_end | 1200 | **900** |

**근거**:
- residency_floor=0.50 기준으로 RR contact EMA가 floor 아래로 내려가면 즉시 강한 penalty
- iter 1201 RR contact 0.277 → EMA ≈ 0.25~0.35 → gap ≈ 0.15~0.25 → penalty ≈ -15 × 0.2 = -3.0/leg
- 4leg 합산 시 RR gap + 다른 leg 합산 → 의미 있는 억제

### 수정 4. cooperation_min_leg_factor 강화

| 항목 | V28.1 | V28.2 |
|------|-------|-------|
| coop_min_leg_factor_target | 0.2 | **0.05** |
| coop_min_leg_ramp_start | 800 | **600** |
| coop_min_leg_ramp_end | 1000 | **800** |

**목적**:
- 최약 다리(RR)가 band 밖이면 cooperation reward를 거의 차단
- 현재 0.2 (80% 감쇠) → 0.05 (95% 감쇠)로 강화
- 3발 exploit 상태에서 cooperation reward 기여를 사실상 0으로 만듦

**근거**:
- iter 1502에서 `four_limb_cooperation`이 reward 기여를 하고 있다면, 이게 3발 exploit을 지지하는 역설적 보상
- RR band 밖 → min_leg_factor 0.05 → cooperation reward ≈ 0 → 3발 exploit 이득 차단

### 수정 5. heartbeat에 residency 지표 추가 (common.py)

**추가할 KPI 필드**:
```
contact_band_residency_fl / fr / rl / rr   (EMA 현재값)
prop_band_residency_rl / rr                 (rear pair만)
rear_pair_residency_gap                     (abs(rl_ema - rr_ema))
```

**추가할 경보**:
- `rear_pair_residency_gap > 0.15` → heartbeat에 ⚠️ 경고 표시
- `contact_band_residency_rr < 0.30` → heartbeat에 🔴 경고 표시

### 4.2 `rewards.py` — 신규 함수 추가 + tensorboard 로그

**신규 함수 1**: `rear_pair_contact_diff_penalty`

```python
def rear_pair_contact_diff_penalty(
    env: ManagerBasedRLEnv,
    diff_threshold: float = 0.15,
    min_vel: float = 0.05,
    asset_cfg: SceneEntityCfg = SceneEntityCfg("robot"),
) -> torch.Tensor:
    """V28.2: RL vs RR current-step contact_ratio 차이를 즉각 패널티.

    EMA 기반이 아닌 현재 step 기준으로 즉각 반응.
    run 재기동 후 EMA 워밍업 사각지대를 보완.
    """
    metrics = compute_v23_raw_metrics(env)
    if not metrics:
        return torch.zeros(env.num_envs, ...)
    rl_contact = metrics["contact_ratio_rl"]
    rr_contact = metrics["contact_ratio_rr"]
    diff = torch.abs(rl_contact - rr_contact)
    gap = torch.clamp(diff - float(diff_threshold), min=0.0)
    return gap * _heading_velocity_gate(env, asset_cfg, min_vel)
```

## 5. 수치 근거 — "왜 이 수치인가"

### rear_symmetry_max -28.0의 근거

V28.1 iter 1502 상황:
- rear contact EMA gap ≈ 0.50 (RL 0.70 vs RR 0.25 기준)
- 현재 penalty: -8.0 × (0.50 - 0.05) = -3.6
- 3발 exploit 추가 이득 추정: 전진속도 기여 + cooperation 기여 ≈ +8~15 units
- 이기려면: -28.0 × (0.50 - 0.05) = **-12.6** → 충분한 억제력

### rear_contact_diff_max -15.0의 근거

iter 1201 시점 즉각 차이 = abs(0.561 - 0.277) = 0.284:
- threshold 0.15 → gap = 0.134
- penalty: -15.0 × 0.134 = **-2.0** per step
- EMA lag 없이 즉각 반응 → EMA 기반 penalty와 함께 누적 효과

### coop_min_leg_factor_target 0.05의 근거

iter 1502에서 `four_limb_cooperation` reward가 만약 +3.0 기여 중이라면:
- min_leg = RR의 current band score ≈ 0 (contact 0.259 < band_low 0.20에 근접)
- factor ≈ 0.05 → cooperation reward ≈ 3.0 × 0.05 = **+0.15** (사실상 차단)
- 이전 0.2 → 3.0 × 0.2 = **+0.6** (여전히 기여)

## 8. 리스크

### 리스크 1. rear_symmetry_max -28.0이 너무 강해 all-leg suppression

**가능성**: RL도 함께 억눌려 초반 4발 진입 자체가 어려워질 수 있음.
**대응**: ramp_start=400으로 Layer C (iter 100~300)가 먼저 4발을 끌어올린 후 작동.
            iter 400 이전에는 rear_symmetry = 0이므로 초반 진입은 보호됨.

### 리스크 2. rear_contact_diff_penalty가 정상 보행 변동을 처벌

trot gait에서 RL/RR는 대각 쌍이므로 순간적으로 contact 비대칭이 발생할 수 있음.
**대응**: diff_threshold=0.15로 소폭 변동은 무시. trot 중 정상 contact 차이는 0.05~0.10 수준.

### 리스크 3. coop_min_leg_factor 0.05로 인한 학습 불안정

cooperation reward가 사실상 차단되면 초반 학습 동력이 약해질 수 있음.
**대응**: ramp_start=600으로 Layer C가 iter 300~600 구간에서 충분히 진입한 후 활성화.

### 리스크 4. tensorboard residency 로그 구현 복잡도

현재 `accumulate_v23_raw_metrics`에서 tensorboard writer 접근 방식 확인 필요.
**대응**: rewards.py에서 직접 writer 접근이 어려우면, heartbeat가 env에서 직접 읽는 방식으로 대안.

## 12. 최종 판단

### V28.2로 결정하는 이유

1. **구조 자체는 유효함** — iter 1000에서 4발 완벽한 상태가 실제로 달성됨

### V29가 필요한 조건

- 다시 다른 다리가 무너짐 (FL 또는 FR이 3번째 collapse 축이 됨)

- iter 400에서 이미 4발 진입 실패 (Layer C 구조 자체 문제)

## 13. 구현 주의사항

1. **`rear_pair_contact_diff_penalty` 학습 영향력 확인**
   threshold 0.10은 onset을 잡기에 좋지만, 실제 학습에 영향력이 충분한지
   코드 리뷰 단계에서 gap 범위와 weight 조합을 검토할 것.
   (gap이 0.01~0.02 수준이면 실질 penalty가 너무 작을 수 있음)

2. **`rear_pair_residency_gap`과 `rear_usage_diff` 정의 구분 명확화**
   - `rear_usage_diff`: 현재 step limb usage 차이 (즉각값)
   - `rear_pair_residency_gap`: EMA contact residency 차이 (장기 누적값)
   heartbeat에 두 값을 함께 노출하되, 레이블을 명확히 구분할 것.

3. **rear symmetry 관련 penalty — iter 700 이전 full-strength 금지**
   `rear_pair_residency_symmetry_penalty`와 `rear_pair_contact_diff_penalty` 모두
   iter 700 이전에 최대 강도로 들어가지 않도록 ramp를 철저히 준수.
   V27.1a의 과강도 선례를 반복하지 말 것.

4. **`front_rear_balance` — V28.2에서 모니터링 전용 유지**
   reward 개입 없이 heartbeat 핵심 모니터링 항목으로만 운영.
   rear symmetry 해결 이후 front-heavy 패턴이 잔존하면 V28.3에서 reward 설계 검토.
