# V28.3_PLAN.md

## 한 줄 정의
**V28.3은 V28.2에서 rear pair 대칭을 달성했지만 앞발이 기둥으로 고정되어 발생한 "앞발 고정 벌레 걸음" 패턴을 해결하는 버전이다.**
핵심 문제는 FL/FR contact가 0.84~0.89까지 올라가도 억제 장치가 없다는 것이며,
front contact cap + front-rear balance 활성화로 해결한다.

## 실패 원인 정확한 정의

### 원인 1. front contact 상한 패널티 부재

`per_leg_contact_target_band` band_high=0.45이지만 초과 시 **패널티 없음**.
FL contact 0.84가 band를 한참 벗어나도 band reward를 못 받을 뿐, 억제력이 없다.

반면 `contact_residency` reward는 높은 contact EMA를 보상:
```
FL residency 0.941 × late_max(4.0) ≈ +3.76/step
FL contact 0.65로 떨어지면: 0.65 × 4.0 ≈ +2.60/step
→ 앞발이 0.84를 유지하는 이득: +1.16/step per leg
```
이 이득을 이길 패널티가 없어 local optimum에 고착.

### 원인 2. front_rear_support_balance_penalty 완전 비활성

```python
weight=0.0  # V27: 비활성
params={"max_diff": 0.50, ...}
```

**weight=0.0** — V27부터 비활성화된 채 V28.2까지 그대로.
max_diff=0.50도 너무 관대해서, 설령 켰더라도 현재 diff=0.372에서는 패널티 미발동.

### 원인 3. contact residency reward가 앞발 고착을 지원

contact_residency는 모든 4발에 동일하게 적용.
앞발이 단순히 땅에 붙어있기만 해도 높은 residency reward를 받는 구조.
FL/FR residency가 0.941/0.967로 RL/RR(0.633/0.605)보다 훨씬 높으며,
이는 penalty 없이 자동으로 달성 가능한 수치.

## V28.3 핵심 수정 사항 (2개)

### 수정 1. `front_pair_contact_cap_penalty` 신규 추가

**목적**: FL/FR contact ratio 상한 초과 시 즉각 패널티. 앞발 고정 local optimum 직접 차단.

**설계**:
- 측정: `contact_ratio_fl`, `contact_ratio_fr` (current-step, EMA 아님)
- contact_cap: **0.65** (soft cap — 이상적 목표값이 아님. 0.84+ 고착 억제용)
- 수식: `penalty = clamp(fl - 0.65, 0) + clamp(fr - 0.65, 0)`
- max weight: **-10.0**
- ramp: **iter 700~1000**

**수치 근거**:
```
iter 1703 기준:
  FL gap = 0.840 - 0.65 = 0.190 → -10.0 × 0.190 = -1.90/step
  FR gap = 0.889 - 0.65 = 0.239 → -10.0 × 0.239 = -2.39/step
  합산 패널티: -4.29/step

residency 이득: +1.16/step per leg → 총 +2.32/step (FL+FR)
패널티(-4.29) > 이득(+2.32) → 앞발 고착 억제력 충분
```

**ramp 타이밍 (iter 700~1000)**:
| iter | alpha | weight | FL gap 기준 패널티 |
|------|-------|--------|-----------------|
| 700 | 0.00 | 0.0 | 0 (시작) |
| 800 | 0.33 | -3.3 | -0.63/step |
| 900 | 0.67 | -6.7 | -1.27/step |
| 1000 | 1.00 | -10.0 | -1.90/step |

→ iter 700 이전 full-strength 없음. rear symmetry 완료 후 개입.

**`band_high=0.45`와의 차이**:
- `band_high`: 이 값 위면 band reward 없음 (소극적 억제)
- `contact_cap=0.65`: 이 값 위면 직접 패널티 (적극적 억제)
- 두 threshold 사이(0.45~0.65)는 band reward도 없고 cap도 없는 "완충 구간" — 정상 trot 변동 허용

### 수정 2. `front_rear_support_balance_penalty` 활성화 + 강화

**목적**: 앞/뒤 usage 편중 억제. contact cap 혼자서 못 잡는 전체적 front-heavy 패턴 보완.

**설계**:
```python
# 현재 (V28.2)
weight=0.0         # 완전 비활성
max_diff=0.50      # 너무 관대

# V28.3
weight=0.0         # curriculum ramp으로 제어
max_diff=0.30      # 0.50 → 0.30
# TRAINING_CONFIG 추가:
front_balance_ramp_start=700
front_balance_ramp_end=1000
front_balance_max=-8.0
```

**수치 근거**:
```
현재 diff = 0.372
max_diff 0.30 → gap = 0.372 - 0.30 = 0.072
full strength: -8.0 × 0.072 = -0.58/step (보조 신호)
```

contact cap(-4.29/step)에 비해 약하지만, 전체적 front-heavy 패턴에 지속 압력.

**역할 정의**: 핵심 해법이 아니라 **late-stage 품질 보정 보조**.
contact cap이 앞발을 내리면 balance penalty는 유지 압력 역할.

## 파일별 변경 내역

### `rewards.py`

**신규 함수**: `front_pair_contact_cap_penalty`

```python
def front_pair_contact_cap_penalty(
    env: ManagerBasedRLEnv,
    contact_cap: float = 0.65,
    min_vel: float = 0.05,
    asset_cfg: SceneEntityCfg = SceneEntityCfg("robot"),
) -> torch.Tensor:
    """V28.3: FL/FR contact ratio 상한 초과 시 패널티.

    앞발 고정 local optimum 차단.
    band_high(0.45)와 다른 역할: band는 소극적 억제, cap은 적극적 패널티.
    contact_cap=0.65는 이상적 목표값이 아니라 0.84+ 고착 억제용 soft cap.
    """
    metrics = compute_v23_raw_metrics(env)
    if not metrics:
        return torch.zeros(env.num_envs, dtype=torch.float, device=env.device)
    fl_contact = metrics["contact_ratio_fl"]
    fr_contact = metrics["contact_ratio_fr"]
    gap = torch.clamp(fl_contact - float(contact_cap), min=0.0) \
        + torch.clamp(fr_contact - float(contact_cap), min=0.0)
    return gap * _heading_velocity_gate(env, asset_cfg, min_vel)
```

## 수치 근거 — "왜 이 수치인가"

### contact_cap=0.65의 근거

```
trot gait 이론적 contact ratio: ~0.50
RL/RR 현재: 0.486~0.510 (건강한 trot 수준)
FL/FR 목표: RL/RR과 유사한 0.50~0.65

0.65는 trot에서 자연스럽게 허용 가능한 최대치.
0.45 (band_high) 보다 여유를 줘 정상 보행 변동(0.45~0.65)은 허용.
```

### front_contact_cap_max -10.0의 근거

```
현재 앞발 고착 이득:
  FL residency(0.941) - 목표 residency(0.65) ≈ 0.29 × late_max(4.0) = +1.16/step
  -10.0 × gap(0.19) = -1.90/step → 이득의 1.64배 → 충분한 억제력

-12.0 기각 이유:
  ramp 중반(iter 850)에서 weight≈-8.0 → gap 0.19 × -8.0 = -1.52/step
  동시에 front_balance도 weight≈-5.3 작동 → 이중 압박
  V27.1a 과강도 선례: 같은 시점에 여러 penalty가 겹치면 경직 발생
```

### front_balance_max -8.0의 근거

```
gap = diff(0.372) - max_diff(0.30) = 0.072
-8.0 × 0.072 = -0.58/step (보조 신호 수준, 과강도 아님)
contact cap(-4.29/step) 대비 8분의 1 수준 → 보조 역할에 적합
```

### ramp_start=700의 근거

V28.2 실측에서 rear_symmetry full strength = iter 700:
```
V28.2 iter 700: rear_usage_diff=0.017, rear_pair_residency_gap 수렴 중
V28.2 iter 800: rear_usage_diff=0.001, 완전 안정
```
iter 700에서 front 제약 시작하면 rear 안정화 이후 개입 가능.
단, V28.3은 fresh start이므로 rear 상태를 보장하기 어려움.
→ ramp_start=700은 V28.2 경험 기반 최선의 추정값.

## 리스크

### 리스크 1. front cap이 학습 경직을 유발
앞발을 갑자기 내리면 안정성(자세)이 흔들릴 수 있음.
**대응**: ramp_start=700, max=-10.0으로 점진적. 안정성 지표(survival_pct) 모니터링.

### 리스크 2. rear symmetry 재붕괴
front 관련 penalty 추가로 전체 reward 구조가 바뀌어 rear가 다시 불안정해질 가능성.
**대응**: rear_symmetry penalty는 V28.2 그대로 유지(-28.0). heartbeat의 rear_pair_residency_gap 경보 유지.

### 리스크 3. contact_cap=0.65가 trot 중 순간 초과를 처벌
trot에서 FL이 순간적으로 0.68이 되는 경우 패널티 발동.
**대응**: current-step 기반이므로 step 단위 패널티는 작음. gap=0.03 × -10.0 = -0.3/step — 허용 범위.

### 리스크 4. front swing incentive 없이 자연 개선이 충분하지 않을 수 있음
contact cap으로 앞발을 내려도 swing이 충분히 늘지 않을 가능성.
**대응**: iter 900 판정에서 FL swing > 0.25 미달 시 V28.3b에서 swing incentive 추가.

## 구현 주의사항

1. **`contact_cap=0.65`는 soft cap이지 목표값이 아님**
   이상적 FL/FR contact는 0.50~0.60. 0.65는 0.84+ 고착을 차단하는 임계값.
   판정 기준에서도 "0.65 미만"이 아니라 "0.50~0.65 범위"가 목표.

2. **`front_pair_contact_cap_penalty`는 `band_high=0.45`와 역할이 다름**
   - band_high: contact > 0.45면 band reward 없음 (소극적 신호)
   - contact_cap: contact > 0.65면 직접 패널티 (적극적 억제)
   - 0.45~0.65 구간은 두 장치 모두 무관 — 정상 trot 완충 구간

3. **front 관련 penalty는 iter 700 이전 full-strength 절대 금지**
   V27.1a 과강도 선례: ramp_start 준수가 핵심. 코드 구현 후 alpha 초기화 값 재확인 필수.

4. **front swing incentive는 이번 턴 보류**
   contact cap 효과 단독 검증이 목적. swing이 자연 개선되지 않으면 V28.3b에서 추가.
   이번 구현에 swing reward를 추가하면 개선 원인 분리 불가능.

5. **rear symmetry 지표 지속 모니터링**
   front 제약 추가 후에도 heartbeat의 `rear_pair_residency_gap`, `rear_usage_diff` 경보 유지.
   rear 불안정 신호 감지 시 front 제약보다 rear 안정화 우선.

6. **supervisor/heartbeat 재시작 필요**
   common.py 변경 없음. env_cfg.py + rewards.py만 수정.
   단, `.env`의 TRAIN_VERSION 변경으로 supervisor 재시작 필요.
