# V28.1_PLAN.md

## V28.1 한 줄 정의
**V28.1은 4발을 target band에 “진입”시키는 버전이 아니라, 600~800에서 실제로 형성된 좋은 4족 상태를 1000 이후에도 “유지”시키는 버전이다.**

즉 V28의 실패 본질은
- entry 실패가 아니라
- **residency(체류) 실패**
였다고 보고 설계한다.

---

## 1. V28 분석을 반영한 핵심 수정 사항

V28 분석 결과, 다음 사실이 확정되었다.

1. **iter 600~800은 실제 성공 구간이었다**
   - 4발 validity pass
   - RL도 충분히 살아 있었음
   - target-band / cooperation reward가 실제로 작동함

2. **iter 1000부터 RL 약세가 시작되었다**
   - 초기 학습 실패가 아니라 후반 약세 형성 시작점

3. **iter 1200부터는 사실상 붕괴 구간이었다**
   - RL이 band 밖으로 밀려나고 회복 없이 collapse로 고착

따라서 V28.1은
- 새로운 floor를 더 넣는 버전이 아니라
- **좋은 상태(600~800)를 잃지 않게 하는 유지 강화판**으로 정의한다.

---

## 2. 기준 checkpoint 재정의

### 기준 checkpoint 1: iter 800
- **best reference checkpoint**
- 가장 중요한 기준점
- 이유: 좋은 상태가 형성된 뒤 일정 시간 유지된 상태

### 기준 checkpoint 2: iter 600
- **early good reference**
- 좋은 상태가 처음 확실하게 확인된 지점

### 비교 checkpoint 3: iter 1000
- **collapse onset reference**
- RL 약세가 시작된 지점

### 비교 checkpoint 4: iter 1200
- **failure entry reference**
- RL 붕괴가 사실상 확정된 지점

즉 V28.1의 모든 분석/구현 기준축은

> **600 ↔ 800 ↔ 1000 ↔ 1200**

으로 고정한다.

---

## 3. V28.1 핵심 목표

V28.1의 목표는 다음 네 가지다.

1. **600~800의 좋은 상태를 기준 정책으로 삼는다**
2. **1000 이후 rear-left가 band 밖으로 빠지는 현상을 조기 차단한다**
3. **rear pair 내부의 장기 비대칭을 억제한다**
4. **cooperation reward가 평균값에 속지 않도록 최약 다리 기준을 강화한다**

즉 V28.1은
- 더 강한 벌점 추가판이 아니라
- **후반 이탈 방지 / 유지 강화판**이다.

---

## 4. V28.1의 핵심 가설

V28 붕괴를 만든 원인은 아래라고 본다.

### 가설 1. Band entry는 성공했지만 band residency가 약했다
V28은 순간적으로 band 안에 들어오는 것은 잘 만들었다.
하지만 특정 다리(RL)가 **장기적으로 band 안에 머무는 것**을 충분히 유도하지 못했다.

### 가설 2. Rear pair 내부 유지 대칭이 약했다
실패의 핵심은 front-rear imbalance보다 먼저
**rear-left vs rear-right의 장기 비대칭 누적**이었다.

### 가설 3. Cooperation reward가 평균에 속았다
3개 다리가 매우 좋고 1개가 점점 나빠져도
평균 기반 cooperation reward는 어느 정도 살아남을 수 있었다.

### 가설 4. 후반 band exit를 막는 장치가 없었다
초기엔 band 진입이 중요했지만,
후반엔 **band 밖으로 천천히 이탈하는 현상**을 더 중요하게 봐야 했는데
그 장치가 없었다.

## 5. V28.1 신규 설계 축

### 5.1 Per-leg band residency
각 다리에 대해 최근 구간에서
- contact가 band 안에 있었던 비율
- propulsion이 band 안에 있었던 비율
- usage가 band 안에 있었던 비율

을 계산한다.

#### 목적
- 순간적 band 진입이 아니라
- **지속적 band 유지**를 선호하도록 만들기

#### 핵심 대상
- 특히 RL residency 하락을 추적하는 데 사용

---

### 5.2 Rear-pair residency symmetry
rear pair 내부에서
- RL residency
- RR residency

차이가 일정 구간 동안 누적되면 penalty를 준다.

#### 목적
- rear-left만 천천히 빠지는 실패 패턴 차단
- rear 내부의 장기 비대칭을 조기 경고

#### 중요
이 항목은 순간 `rear_prop_diff`보다 우선한다.
이번 실패는 한 번의 스파이크가 아니라 **시간 누적형 붕괴**였기 때문이다.

---

### 5.3 Min-leg weighted cooperation
기존 cooperation reward는 유지하되,
그 값에 **최약 다리(min-leg)의 상태**를 반영한다.

#### 목적
- 3개 좋고 1개 나쁜 상태에서 평균 cooperation reward가 과도하게 유지되는 것 방지

#### 원칙
- 완전 차단이 아니라 soft multiplicative factor
- min-leg가 낮을수록 cooperation reward를 점진적으로 감쇠

---

### 5.4 Late-phase band exit penalty
좋은 상태가 만들어진 이후(특히 iter 800 이후),
특정 다리의 residency가 reference 대비 하락하면 penalty를 준다.

#### 목적
- good phase 이후 발생하는 local optimum drift 차단
- “좋은 상태를 만든 뒤 잃는 문제” 해결

#### 적용 철학
- 초반에는 off
- 후반에만 gradual on
- sudden full-strength 금지

## 8. Curriculum 재설계

핵심 원칙은 **초반 생성 / 후반 유지 분리**다.

### Stage 1: iter 0~200
목표:
- V28처럼 학습이 죽지 않게 함
- 4발 모두 최소 floor 위로 올리기

구성:
- 기존 V28 구조 유지
- residency 관련 항목 off 또는 매우 약함
- band exit penalty off

### Stage 2: iter 200~600
목표:
- target band 진입
- 4발 cooperation 형성

구성:
- target-band reward 정상 작동
- cooperation reward 정상 작동
- residency reward는 매우 약하게만 시작 가능

### Stage 3: iter 600~800
목표:
- good phase 확인
- best reference checkpoint 확보

구성:
- residency reward 본격 on
- rear pair symmetry penalty 약하게 on
- iter 800 자동 보존

### Stage 4: iter 800~1000
목표:
- good phase 유지
- RL 약세 조기 감시

구성:
- residency reward 강화
- cooperation min-leg factor 활성화 시작
- band exit penalty very light on

### Stage 5: iter 1000~1200
목표:
- collapse onset 조기 차단

구성:
- rear pair symmetry penalty 강화
- band exit penalty gradual on
- RL residency 하락 시 즉시 경고

### Stage 6: iter 1200+
목표:
- 후반 붕괴 방지
- 장기 유지

구성:
- residency / symmetry / exit penalty fully active
- reference 대비 이탈 지속 시 훈련 중단 검토

## 9. 권장 초기 수치 방향

### 9.1 Residency 계산
- 최근 `N` step hard window보다 **EMA**가 우선
- 이유: 구현이 단순하고 drift 감지가 빠름

### 9.2 Cooperation min-leg factor
- hard cutoff 금지
- soft multiplicative factor 사용

예시 개념:
- 평균 cooperation score × min_leg_factor
- min_leg_factor는 최약 다리의 band score 또는 residency에서 산출

### 9.3 Rear pair symmetry
- 작은 차이는 무시
- 일정 차이 이상이 일정 시간 누적될 때만 penalty 활성화

### 9.4 Band exit penalty
- iter 800 이후 gradual on
- iter 1000 이후 의미 있는 수준
- iter 1200 이후 fully active 가능

### 9.5 기준 수치 참조
정확한 threshold는
- iter 600
- iter 800
- iter 1000
- iter 1200

실측 비교표에서 최종 결정한다.

## 🔴 Critical — 설계 결정 없이 구현 착수 불가

### C-1. EMA 상태 저장 방식 미결 (Section 9.1, 5.1)

V28에는 EMA가 전혀 없다. Rolling window(contact sensor history)만 존재한다.
EMA를 새로 구현하려면 반드시 결정이 필요하다.

- EMA state를 **episode 단위로 리셋**할 것인지, **에피소드를 가로질러 유지**할 것인지
- 에피소드 리셋 시 초기화하면 “장기 residency” 측정 불가
- 에피소드를 넘겨 유지하면 에피소드 경계 왜곡 발생
- V28의 episode sums(`_v23_raw_metric_episode_sums`)는 리셋됨 — 별도 tensor 필요

**결정 필요**: EMA를 에피소드 유지로 가는가, 에피소드 내 window로 구현하는가?

---

### C-2. `late_phase_band_exit_penalty`의 reference baseline 정의 없음 (Section 5.4)

“reference 대비 하락하면 penalty”라고 했으나, reference가 무엇인지 정의되지 않았다.

- **Option A**: iter 800 실측값을 상수로 박음 — feedback_no_hardcoding 위반
- **Option B**: iter 800 도달 시 EMA값을 동적으로 저장 — 복잡한 state 관리 필요
- **Option C**: reference 없이 residency 하락 속도(gradient)만 감지

**결정 필요**: A/B/C 중 어느 방식인가?

---

### C-3. Stage별 다중 분기점 ramp 구조 없음 (Section 8)

기존 V28 ramp 시스템은 2-point linear (`ramp_start → ramp_end`)만 지원한다.

새 multi-breakpoint ramp 함수가 필요하거나, 기존 ramp를 여러 개 조합해야 한다.

**결정 필요**: multi-breakpoint ramp를 신규 설계할 것인가, 기존 방식 조합으로 대응할 것인가?

## 🟡 Important — 방향 확인 후 구현 가능

### I-1. `cooperation_min_leg_factor` 입력값 “또는” 미결 (Section 9.2)

**확인 필요**: 단순 차이로 충분한가, 추가 누적이 필요한가?

# 기획/분석팀 피드백

좋습니다.
개발자 피드백은 타당합니다. 지금 필요한 건 “추가 아이디어”가 아니라 구현 가능하도록 설계 결정을 잠그는 것입니다.

아래처럼 결정사항을 확정하면 됩니다.

⸻

V28.1 구현 결정안

결론

V28.1은 “복잡한 새 프레임워크”로 가지 말고, 기존 V28 구조 위에 최소한의 상태(state)만 추가하는 방식으로 구현합니다.
즉:
	•	EMA는 에피소드 내부에서만 유지
	•	baseline은 iter 800 고정 하드레퍼런스가 아니라, good-phase residency EMA
	•	multi-breakpoint ramp는 새 ramp 함수 추가 없이, term 분리로 해결

이렇게 가는 게 가장 현실적이고 안전합니다.

⸻

1. EMA 저장 방식 — 결정

결정

EMA는 episode 단위로 리셋합니다. 에피소드를 가로질러 유지하지 않습니다.

이유

에피소드를 넘겨 EMA를 유지하면:
	•	episode boundary 왜곡
	•	reset 이후 이전 episode 상태가 섞임
	•	디버깅이 어려움

지금 필요한 residency는 “정책의 장기 철학적 상태”가 아니라,
한 episode 안에서 특정 다리가 band 안에 안정적으로 머무는가를 보는 것입니다.

즉 V28.1의 residency는:
	•	글로벌 런 전체 장기기억이 아니라
	•	episode 내부 지속성 측정치

로 정의합니다.

구현 원칙
	•	각 env마다 per-leg EMA tensor 유지
	•	reset 시 해당 env만 초기화
	•	기존 episode sums와 별도 tensor로 관리

정리 문장

EMA residency는 per-env, per-episode 상태로 관리하고, env reset 시 초기화한다.

⸻

2. late_phase_band_exit_penalty baseline — 결정

결정

Option B/C 절충으로 갑니다.
즉,
	•	iter 800 값을 하드코딩하지 않음
	•	훈련 중 특정 시점의 고정 snapshot 저장도 하지 않음
	•	대신 current EMA residency가 good-phase minimum 기준 아래로 떨어지는지를 late-phase에서 직접 평가합니다

더 정확히

baseline은 “iter 800 고정 수치”가 아니라:

good-phase 기준 band residency threshold

입니다.

즉 late-phase_band_exit_penalty는
“reference checkpoint 대비 절대 차이”가 아니라
	•	현재 시점이 late phase이고
	•	해당 다리 residency가
	•	good-phase에서 기대되는 최소 residency 기준 이하로 내려갔는가

를 봅니다.

왜 이렇게 결정하나
	•	iter 800 하드레퍼런스 저장은 구현 복잡도가 커짐
	•	checkpoint 값 동적 보존은 상태 관리가 무거움
	•	반면 current EMA residency + late-phase threshold 방식은 단순하고 안정적

구현 개념

예시:
	•	late_phase_band_exit_penalty = f(max(0, residency_floor_late - current_residency))
	•	여기서 residency_floor_late는 600/800 분석값 기반 threshold

즉 “reference gap”이 아니라
late-phase expected residency floor 미달을 패널티로 봅니다.

정리 문장

late_phase_band_exit_penalty는 iter 800 고정 snapshot 기반이 아니라, late phase에서 현재 per-leg residency가 사전에 정의한 residency floor below로 내려갈 때 활성화한다.

⸻

3. multi-breakpoint ramp 구조 — 결정

결정

새 multi-breakpoint ramp 함수는 만들지 않습니다.

대신:
	•	term을 역할별로 분리하고
	•	각 term마다 기존 2-point linear ramp를 따로 적용합니다

즉 Stage 3/4/5를 하나의 복잡한 ramp로 만들지 말고,
다음처럼 나눕니다.

예시
	•	residency_reward_early → 600~800
	•	residency_reward_late → 800~1000
	•	band_exit_penalty → 1000~1200

이렇게 하면 기존 ramp 시스템만으로 충분합니다.

이유
	•	지금 코드베이스는 2-point linear에 맞춰져 있음
	•	새 ramp 엔진 도입은 버그 위험 증가
	•	term 분리 방식이 더 단순하고 디버깅 쉬움

정리 문장

V28.1의 stage 분화는 새 ramp 엔진이 아니라, 항목 분리 + 기존 2-point ramp 조합으로 구현한다.

⸻

중요하지만 구현 중 결정 가능한 항목들

4. cooperation_min_leg_factor 입력값 — 결정

결정

1차 구현은 residency가 아니라 current band score 기반으로 갑니다.

즉:
	•	최약 다리의 현재 step band score 사용
	•	EMA residency를 직접 입력으로 넣지 않음

이유
	•	EMA를 cooperation factor까지 연결하면 구조가 복잡해짐
	•	1차 목적은 평균 cooperation reward가 최약 다리를 무시하지 못하게 하는 것
	•	current band score만으로도 충분히 그 효과를 볼 수 있음

단서

후속 버전에서 필요하면 residency 기반 cooperation factor로 확장 가능

정리 문장

cooperation_min_leg_factor는 1차 구현에서 current per-leg band score의 min값 기반 soft factor로 구현한다.

⸻

5. rear_pair_residency_symmetry_penalty 누적 방식 — 결정

결정

이중 EMA는 하지 않습니다.

즉 penalty는 단순히:
	•	abs(RL_residency - RR_residency)

기반으로 계산합니다.

이유
	•	residency 자체가 이미 시간 누적값
	•	차이의 EMA까지 또 만들면 과도하게 복잡
	•	디버깅과 해석성이 떨어짐

정리 문장

rear_pair_residency_symmetry_penalty는 RL/RR residency 차이의 절대값을 직접 사용하며, 별도의 이중 EMA는 도입하지 않는다.

⸻

6. iter 800 자동 보존 방식 — 결정

결정

기존 checkpoint/video 저장 주기로 iter 800이 자동 생성되는지 먼저 확인하고, 안 되면 별도 one-shot 저장 로직 추가입니다.

하지만 설계 문서 기준으로는 명확히:
